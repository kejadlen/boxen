# WeeChat with wee-slack

This evaluation covers running [WeeChat][weechat] on imperishable-night
as an always-on Slack client through the [wee-slack][wee-slack] plugin.
It connects to both personal workspaces and a work workspace, and every
client reaches it over WeeChat's relay. IRC stays on soju and gamja for
now. Whether WeeChat later connects through soju or replaces it is out of
scope. Nothing is decided yet. The main cost is that each Slack token
acts as the user across a whole workspace.

[weechat]: https://weechat.org/
[wee-slack]: https://github.com/wee-slack/wee-slack

## wee-slack's state

wee-slack is maintained, but slowly. As of 2026-11-19 the repository
isn't archived, its last commit landed on 2026-08-17, and it has 116
open issues. The last tagged release is v2.11.0, from 2024-10-09.

The flake's nixpkgs packages the following versions:

| Package | Version |
|---|---|
| `weechat` | 4.10.1 |
| `weechatScripts.wee-slack` | 2.11.0-unstable-2026-01-07 |

An image built from those packages avoids depending on a third-party
image.

## Shape

The service would follow the pattern that soju already uses:

- `weechat-headless` runs as an oci-container with no terminal, so the
  relay is the only way in.
- The container shares a `weechat` podman network with Caddy and nothing
  else.
- A `weechat` Caddy site uses `import ts weechat` and `tailscale_auth`,
  and proxies to the relay's websocket. The relay password is a second
  layer.
- Clients are a local WeeChat, weechat-android, or Glowing Bear.
- `/var/lib/weechat` is covered by the existing `/var/lib` backup
  ([backup](../backup.md)), which includes WeeChat's secured data.

`tailscale_auth` identifies a peer by its tailnet address rather than by
a cookie, so it should work for clients other than a browser. Nobody has
checked this with weechat-android yet.

## Tokens

wee-slack accepts the following two kinds of token:

| Token | How it's obtained | Revocable | Fits |
|---|---|---|---|
| OAuth | wee-slack's OAuth flow; needs admin approval if the workspace restricts app installs | Yes | The personal workspaces |
| Session | Copied from the web client, along with its `d` cookie | No | The work workspace, which restricts app installs |

The wee-slack README warns that session tokens "can't be revoked" and
"may stop working at any time." The work token is a secret that reaches
past imperishable-night and can't be revoked if it leaks, so it belongs
under [risk 4](../threat-model.md#4-a-linodes-secrets-reach-past-it) in
the threat model. Whether the work workspace's policy allows a
third-party client also needs checking before setup.

By default, wee-slack stores tokens in plain text in the
`plugins.var.python.slack.slack_api_token` option. Its README instead
puts each token in WeeChat's [secured data][secured-data] with `/secure
set` and sets the option to `${sec.data.<name>}`. `/slack register`
writes an OAuth token back into the plain option, so each new OAuth
token has to be moved by hand.

Secured data is encrypted in `sec.conf` with a passphrase. WeeChat reads
the passphrase from the `WEECHAT_PASSPHRASE` environment variable, so
sops only has to hold the passphrase. It would reach the container
through `environmentFiles` and a sops template, the way homebox's and
ketchup's secrets do. The tokens themselves would be entered once over
the relay with `/secure set` and would never be stored in sops.

The passphrase sits on the same host as `sec.conf`, so a foothold on
imperishable-night still gets the tokens. The encryption protects copies
of `sec.conf`, such as the restic backups. WeeChat prompts for the
passphrase when it's missing or wrong. The guide doesn't say what
`weechat-headless` does when it has no terminal to prompt on.

[secured-data]: https://weechat.org/files/doc/weechat/stable/weechat_user.en.html#secured_data

## Against the self-hosting pattern

The following list weighs the service against the criteria in
[self-hosting](../self-hosting.md#weighing-a-new-service):

- It holds no data worth keeping. Slack keeps the history, and WeeChat
  holds only configuration and logs. The reason to run it is a better
  client, not owning the data.
- It's the small option in its category: one process with a plugin.
- It fits the sign-in only partly. `tailscale_auth` can sit in front,
  but the relay still needs its own password.
- It fails the access test. Each token acts as the user across a whole
  workspace, much like the whole-mailbox token that the pattern warns
  about. A Slack client can't have narrower access, so the integration
  can't change shape to avoid it. This is the main cost, especially for
  the work token, which can't be revoked.

## Open questions

  it has no terminal to prompt on?
- Does weechat-android connect through Caddy's websocket proxy with
  `tailscale_auth` in front?
- Is Glowing Bear still maintained, or does the browser need another
  relay client?
